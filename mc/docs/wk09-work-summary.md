# รายงานสรุปผลการทำงานสัปดาห์ที่ 9 (Week 9 Work Summary)
**โปรเจกต์:** Cafe POS System

ในสัปดาห์ที่ 9 ได้มีการนำเอาผลการวิเคราะห์จาก Requirement, Use Case, และ Database Schema (สัปดาห์ก่อนหน้า) มาลงมือเขียนโค้ดจริง (Implementation) โดยมุ่งเน้นไปที่การวางโครงสร้าง API และจัดการลอจิกทางธุรกิจ (Business Logic) ที่มีความซับซ้อน ได้แก่ การตัดสต็อกแบบสูตรอาหาร และการป้องกันความผิดพลาดของข้อมูลด้วย Database Transaction

## 1. การออกแบบและเอกสาร (Documentation)
- **สร้าง `wk09.md`**: เขียนอธิบาย Business Rules (BR-01 ถึง BR-04) ที่เกี่ยวกับการสร้างออเดอร์, จัดทำ Sequence Diagram สำหรับการยิง API `POST /api/orders`, และเขียนตารางจำแนก Message เพื่อให้เห็นภาพการส่งต่อข้อมูลระหว่าง UI, Controller, Model และ Database

## 2. การปรับปรุงฐานข้อมูล (Database Schema & Seed)
- **แก้ปัญหา IDOR (Insecure Direct Object Reference)**: ทำการเพิ่มคอลัมน์ `branch_id` เข้าไปในตาราง `menu_items` เพื่อผูกว่าเมนูนี้เป็นของสาขาไหน ป้องกันไม่ให้แคชเชียร์สาขาหนึ่ง เผลอไปแก้หรือสั่งเมนูของอีกสาขาหนึ่ง
- **รองรับการยกเลิกบิล (Soft Delete)**: เพิ่มสถานะ `'voided'` ลงใน ENUM ของคอลัมน์ `payment_status` ในตาราง `orders` เพื่อให้รองรับการเก็บประวัติบิลที่ถูกยกเลิก แทนการลบทิ้ง (Hard Delete) แบบเดิม
- **ปรับหลักการ Normalization (3NF)**: ถอดคอลัมน์ที่เป็น Derived Value (`subtotal_amount`, `total_amount`, `change_amount`) ออกจากตาราง `orders` อย่างถาวร เพื่อป้องกันปัญหา Update Anomaly ตามข้อกำหนดหัวข้อ 3.2 และเปลี่ยนไปใช้การคำนวณสดด้วยคำสั่ง `SUM` ผ่านการ JOIN ข้อมูล
- **ปรับปรุง `seed.sql`**: แก้ไขปัญหาภาษาไทยเป็นภาษาต่างดาว (`SET NAMES utf8mb4;`) และอัปเดตข้อมูลจำลองใหม่ทั้งหมดให้สอดคล้องกับโครงสร้างล่าสุด เพื่อให้พร้อมทดสอบตัดสต็อกได้ทันที (มีสูตรชาไทยและลาเต้)

## 3. พัฒนาระบบจัดการเมนู (Menu CRUD API)
- สร้างโครงสร้างแบบ MVC ได้แก่ `menuRoutes.js`, `menuController.js`, และ `menuModel.js`
- เขียน API ให้รองรับ GET, POST, PUT, DELETE 
- **Security Logic**: บังคับให้หน้าบ้านต้องส่ง `branchId` มาทุกครั้ง และ Backend จะทำการ `WHERE branch_id = ?` เพื่อป้องกันการดึงข้อมูลเมนูข้ามสาขา

## 4. พัฒนาระบบสั่งซื้อออเดอร์และตัดสต็อก (Order API & Transactions)
รื้อโครงสร้างโค้ดเดิมจาก Sprint 1 และเขียนใหม่ทั้งหมดให้เป็นระบบออเดอร์ระดับโปรดักชัน:
- **`POST /api/orders` (สร้างออเดอร์)**:
  - **Group Items**: ถ้ารับออเดอร์เมนูเดียวกันซ้ำมา (เช่น ชาไทยบรรทัดละแก้ว 3 บรรทัด) ระบบจะจับรวบยอด (Quantity = 3) ให้อัตโนมัติ (ตาม BR-02)
  - **Dynamic Stock Calculation**: ยิงคำสั่งไปดึง "สูตรอาหาร" จากตาราง `menu_item_ingredients` มาคูณกับจำนวนแก้ว เพื่อหาว่าต้องใช้ใบชากี่กรัม นมข้นกี่มิลลิลิตร
  - **Database Transactions (ACID)**: นำเอา `BEGIN`, `COMMIT`, `ROLLBACK` มาใช้ครอบการเขียนข้อมูล 5 ตารางพร้อมกัน (`orders`, `order_items`, `ingredients`, `stock_movements`, `receipts`) หากเกิด Error กลางคัน ระบบจะตีกลับข้อมูลทั้งหมด ป้องกันสต็อกหายแต่ไม่ได้เงิน
  - **Low Stock Alerts**: แจ้งเตือนกลับไปยังหน้าบ้านอัตโนมัติหากสต็อกวัตถุดิบชิ้นไหนลดลงต่ำกว่า `low_stock_threshold`
- **`DELETE /api/orders/:id` (ระบบยกเลิกบิล / Void Order)**:
  - ยกเลิกการใช้ Hard Delete (ลบข้อมูลทิ้ง) และเปลี่ยนเป็นระบบ **Soft Delete** (เปลี่ยน `payment_status = 'voided'`) เพื่อให้สรรพากร/บัญชียังตรวจสอบประวัติได้
  - **Auto-Restore Stock**: คืนค่าวัตถุดิบเข้าสต็อกอัตโนมัติ 100% พร้อมบันทึกประวัติการคืนใน `stock_movements` ว่าเป็น `'adjustment'`
  - **Bug Prevention**: เขียนลอจิกดักจับห้ามกดยกเลิกบิลที่เคยถูก Void ไปแล้วซ้ำสอง เพื่อป้องกันบั๊ก "การคืนสต็อกเบิ้ล"
  - รองรับข้อกำหนดการทำงานจริง: หากบาริสต้าทำเครื่องดื่มเสร็จแล้ว จะไม่อนุญาตให้กดยกเลิกบิล
