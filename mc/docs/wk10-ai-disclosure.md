### 5. ผลลัพธ์จาก AI:

AI ช่วยสร้างหน้าเว็บ 5 หน้า ได้แก่ หน้า POS รับออเดอร์ (เลือกเมนูจากการ์ดรูป ใส่ส่วนลด รับเงิน คิดเงินทอน ออกใบเสร็จ), หน้าจัดการเมนู (เพิ่ม/แก้ไข/ลบ อัปโหลดรูป กำหนดสูตรวัตถุดิบ), หน้าสต็อกวัตถุดิบ, หน้าแดชบอร์ดรายงานยอดขาย และหน้าเข้าสู่ระบบ ทุกหน้าเชื่อมกับ API ที่ทำไว้ในสัปดาห์ที่ 9 และมีตัวเลือกสาขา

ฝั่ง backend AI ช่วยเพิ่ม API ที่หน้าเว็บต้องใช้ ระบบล็อกอิน JWT พร้อมแยกสิทธิ์เจ้าของ/แคชเชียร์ (บังคับที่ server ไม่ใช่แค่ซ่อนปุ่ม), การออกเลขคิวที่ไม่ซ้ำแม้กดชำระเงินพร้อมกัน, และการยกเลิกออเดอร์ที่คืนสต็อกเฉพาะกรณีที่ยังไม่เริ่มทำ

ส่วนเอกสาร AI ช่วยร่างตาราง I/O ของฟอร์ม รูปแบบใบเสร็จและรายงาน และ Sequence Diagram ร่างของ `GET /api/reports/sales` (ยังไม่ implement จริง ไว้ทำในสัปดาห์ที่ 13)

### 6. การปรับแต่งของนิสิตเอง:

นิสิตเป็นผู้กำหนดทิศทาง เช่น เลือกเทมเพลต POS ที่ต้องการ, ตัดสินใจให้มีระบบล็อกอินและกำหนดว่าเจ้าของกับแคชเชียร์ทำอะไรได้บ้าง, กำหนดให้ใช้ JWT ตามที่เรียนในคาบ, ตัดสินใจเรื่องเลขคิวรายวัน, ตั้งชื่อร้านและสาขา และสั่งแก้ปัญหาที่เจอตอนใช้งานจริง (ช่องค้นหาตัวอักษรทับกัน, เวลาต้องเป็นเวลาไทย, dropdown สาขาว่าง, ไฟล์ `.env`)

นิสิตทดสอบการทำงานเอง เช่น รัน `schema.sql` / `seed.sql` ใหม่, ลองล็อกอินแต่ละบัญชี, ลองสั่งซื้อ/ยกเลิกออเดอร์ และตรวจว่าตรงกับ Acceptance Criteria ของสัปดาห์ที่ 4 ส่วน Wireframe Mid-Fi วาดโดยสมาชิกในกลุ่มเอง ไม่ได้ให้ AI วาด

นิสิตตัดสินใจเองว่าจะ **ยังไม่แก้** เรื่องวัตถุดิบที่ใช้ร่วมกันทุกสาขา (สต็อกก้อนเดียว) เพราะ schema สัปดาห์ที่ 7 ออกแบบไว้แบบนั้น และจะไม่เปลี่ยนเลข `order_id` ให้เป็นรายสาขา

### 7. เหตุผลในการใช้ AI:

หน้าเว็บมีหลายหน้าและต้องเชื่อมกับ API หลายตัว ใช้ AI ช่วยเขียนโค้ดส่วนที่ซ้ำและยาว (HTML/CSS/JS) เพื่อให้เหลือเวลาไปตรวจว่า UI ตรงกับ Use Case และ Acceptance Criteria และช่วยตรวจจุดที่พลาดง่าย เช่น การแยกสิทธิ์ที่ฝั่ง server, การกัน race ตอนออกเลขคิว, และการคืนสต็อกตอนยกเลิกออเดอร์

AI เป็นเครื่องมือช่วยเขียนและตรวจสอบ การตัดสินใจเรื่องการออกแบบและการนำไปใช้ใน repository เป็นของนิสิต
