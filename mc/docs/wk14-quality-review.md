| 5. Race Condition | ถ้ามีคนทำรายการพร้อมกัน ข้อมูลยังถูกต้องไหม (เช่น 2 เครื่องขายของชิ้นสุดท้ายพร้อมกัน) |

## 2. จุดที่พบความเสี่ยง

### ความเสี่ยง #1

- **Endpoint ที่เกี่ยวข้อง:** `POST /api/orders` (สร้างออเดอร์)
- **Checklist ข้อที่ไม่ผ่าน:** ข้อ 5 Race Condition (คำขอชนกัน)
- **รายละเอียดความเสี่ยง:** ระบบ "ดูสต็อกก่อน แล้วค่อยหักสต็อกทีหลัง" โดยไม่ดูซ้ำตอนหัก ถ้าครัวซองต์เหลือ 1 ชิ้น แล้วมี 2 เครื่องกดชำระเงินพร้อมกัน ทั้งสองเครื่องเห็นว่า "ยังเหลือ 1" จึงผ่านทั้งคู่ ผลคือขายของที่ไม่มีแล้วสต็อกติดลบ ทดสอบจริง: ตั้งสต็อกเหลือ 1 แล้วยิง 6 ออเดอร์พร้อมกัน ระบบรับครบทั้ง 6 ใบ สต็อกกลายเป็น −5
- **ระดับความรุนแรง:** **High** (แก้แล้ว)

### ความเสี่ยง #2

- **Endpoint ที่เกี่ยวข้อง:** `POST /api/orders`
- **Checklist ข้อที่ไม่ผ่าน:** ข้อ 1 Input Validation (ตรวจข้อมูลที่ส่งเข้ามา)
- **รายละเอียดความเสี่ยง:** ฝั่งระบบหลังบ้านไม่ได้ตรวจเอง ไปพึ่งหน้าเว็บอย่างเดียว ถ้าส่งคำขอตรง ๆ จะเกิดปัญหา: เลือก "ทานที่ร้าน" โดยไม่ใส่เลขโต๊ะก็รับออเดอร์ (ขัดกับเกณฑ์ของ US-02), เลขโต๊ะยาวเกิน 10 ตัวอักษรทำให้ระบบพัง (ตอบ 500), และจำนวนเงินที่รับเป็นข้อความ เช่น `"abc"` ก็ทำให้ระบบพังหรือถูกรับไว้ทั้งที่ไม่ใช่ตัวเลข
- **ระดับความรุนแรง:** **Medium** (แก้แล้ว)

### ความเสี่ยง #3

- **Endpoint ที่เกี่ยวข้อง:** ทุก endpoint ที่รับข้อมูลแบบ JSON (`POST` / `PUT`)
- **Checklist ข้อที่ไม่ผ่าน:** ข้อ 4 Error Handling (จัดการข้อผิดพลาด)
- **รายละเอียดความเสี่ยง:** ถ้าส่งข้อมูลที่รูปแบบเสีย (JSON ไม่ครบ) ระบบจะตอบเป็นหน้าเว็บที่แสดงข้อความภายในของระบบ เช่น ที่อยู่ไฟล์และชื่อไลบรารี ผู้ไม่หวังดีเอาไปใช้ศึกษาจุดอ่อนได้
- **ระดับความรุนแรง:** **Medium** (แก้แล้ว)

### ความเสี่ยง #4

- **Endpoint ที่เกี่ยวข้อง:** `POST/PUT /api/menu`, `POST/PUT /api/ingredients`, `POST /api/ingredients/:id/restock`, `GET /api/orders`, `GET /api/reports/sales`
- **Checklist ข้อที่ไม่ผ่าน:** ข้อ 1 Input Validation
- **รายละเอียดความเสี่ยง:** ไม่ตรวจ "ขนาด" ของค่าที่ส่งมา ถ้าส่งชื่อเมนูยาว 200 ตัวอักษร, ราคา 1e20 (ใหญ่เกินไป), เติมสต็อก 1e20 หรือวันที่ที่ไม่มีจริง (`2026-13-45`) ระบบจะตอบ 500 แทนที่จะบอกว่า "ข้อมูลไม่ถูกต้อง" (ข้อมูลไม่เสียหายและไม่รั่ว)
- **ระดับความรุนแรง:** **Low**

### ความเสี่ยง #5

- **Endpoint ที่เกี่ยวข้อง:** `POST /api/uploads/menu-image` (อัปโหลดรูปเมนู)
- **Checklist ข้อที่ไม่ผ่าน:** ข้อ 1 Input Validation
- **รายละเอียดความเสี่ยง:** ตรวจแค่ชนิดไฟล์ที่ผู้ใช้แจ้งมาและขนาด ไม่ตรวจเนื้อไฟล์จริง ทดสอบส่งไฟล์ HTML โดยแจ้งว่าเป็นรูป PNG ระบบก็รับไว้ (ความเสี่ยงต่ำเพราะทำได้เฉพาะเจ้าของร้าน และเบราว์เซอร์ไม่รันไฟล์ชนิดนี้เป็นโปรแกรม)
- **ระดับความรุนแรง:** **Low**

### ความเสี่ยง #6

- **Endpoint ที่เกี่ยวข้อง:** `POST /api/auth/login` และการยืนยันตัวตนทั้งระบบ
- **Checklist ข้อที่ไม่ผ่าน:** – (อยู่นอก Checklist ทั้ง 5 ข้อ)
- **รายละเอียดความเสี่ยง:** (1) ตัวนับการล็อกอินผิดเก็บไว้ในหน่วยความจำ จึงหายเมื่อรีสตาร์ตระบบ (2) กด "ออกจากระบบ" เป็นแค่ลบบัตรผ่าน (token) ในเบราว์เซอร์ ถ้าบัตรผ่านหลุดไปจะยังใช้ได้ครบ 12 ชั่วโมง (3) บัตรผ่านเก็บใน `localStorage` ของเบราว์เซอร์
- **ระดับความรุนแรง:** **Low**

**ที่ผ่านและยืนยันด้วยการรันจริง:**

- **SQL Injection:** ลองพิมพ์คำสั่งแปลก ๆ (`' OR '1'='1`, `1 OR 1=1`, ชื่อเมนูที่มี `DROP TABLE`) แล้วไม่เกิดผล เพราะทุกคำสั่งฐานข้อมูลส่งค่าผ่านช่อง `?` ไม่ได้ต่อข้อความเข้ากับคำสั่ง
- **IDOR:** แคชเชียร์สาขา 1 เปิด/ยกเลิกออเดอร์ของสาขา 2 ได้ผล "ไม่พบ" (404), ดูเมนูสาขา 2 ได้ผล "ไม่มีสิทธิ์" (403), และถ้าแอบใส่ `branchId` ปลอมมาในคำขอ ระบบจะใช้สาขาจากบัตรผ่านแทน

## 3. การแก้ไขที่ทำจริง

แก้ความเสี่ยงสูงสุด **#1** และอีก 2 จุดเล็กที่เกี่ยวข้อง (#2, #3)

### แก้ไข #1: ป้องกันสต็อกติดลบเมื่อมีออเดอร์พร้อมกัน

**แนวคิด:** เปลี่ยนจาก "ดูสต็อกก่อน แล้วค่อยหัก" (สองขั้นตอนที่มีช่องว่างให้คนอื่นแทรก) เป็น "ดูและหักในคำสั่งเดียว" โดยเพิ่มเงื่อนไข `stock_quantity >= ?` ถ้ามี 2 ออเดอร์หักของชิ้นเดียวกันพร้อมกัน ฐานข้อมูลจะให้ออเดอร์แรกทำก่อน ออเดอร์ที่สองต้องรอ แล้วดูจำนวนล่าสุด ถ้าไม่พอก็ยกเลิกทั้งออเดอร์และแจ้ง "วัตถุดิบไม่เพียงพอ"

**โค้ดก่อนแก้** (`src/models/orderModel.js`):

```js
// หักสต็อกเลย ไม่ดูว่าพอหรือไม่
await conn.query(
  `UPDATE ingredients SET stock_quantity = stock_quantity - ? WHERE ingredient_id = ?`,
  [quantityUsed, ingredientId]
);
```

**โค้ดหลังแก้** (`src/models/orderModel.js` และ `src/controllers/orderController.js`):

```js
// หักเฉพาะเมื่อของพอ (AND stock_quantity >= ?)
const [result] = await conn.query(
  `UPDATE ingredients SET stock_quantity = stock_quantity - ?
   WHERE ingredient_id = ? AND stock_quantity >= ?`,
  [quantityUsed, ingredientId, quantityUsed]
);
if (result.affectedRows === 0) {
  return false; // ของไม่พอ -> ยกเลิกทั้งออเดอร์ แล้วตอบ 400
}
```

**ผลทดสอบ** (ตั้งครัวซองต์เหลือ 1 ชิ้น แล้วยิง 6 ออเดอร์พร้อมกัน):

| | รับออเดอร์ได้ | ถูกปฏิเสธ | ออเดอร์ที่ถูกบันทึก | สต็อกหลังทดสอบ |
|---|---|---|---|---|
| ก่อนแก้ | 6 | 0 | 6 | **−5** (ติดลบ) |
| หลังแก้ | **1** | **5** | **1** | **0** |

### แก้ไข #2: ให้ระบบหลังบ้านตรวจข้อมูลของ `POST /api/orders` เอง

**โค้ดก่อนแก้:** ตรวจแค่ว่า `amountReceived` ไม่ว่างและไม่ติดลบ และส่งเลขโต๊ะไปบันทึกโดยไม่ตรวจ

**โค้ดหลังแก้** (`src/controllers/orderController.js`):

```js
// เงินที่รับต้องเป็นตัวเลขจริง ๆ
if (typeof amountReceived !== "number" || !Number.isFinite(amountReceived) || amountReceived < 0) {
  return res.status(400).json({ error: "ต้องระบุ amountReceived เป็นตัวเลขที่ไม่ติดลบ" });
}
// ทานที่ร้านต้องมีเลขโต๊ะ และไม่เกิน 10 ตัวอักษร
if (orderType === "dine_in") {
  const tableText = typeof tableNumber === "string" ? tableNumber.trim() : "";
  if (tableText === "") return res.status(400).json({ error: "กรุณาระบุเลขโต๊ะ" });
  if (tableText.length > 10) return res.status(400).json({ error: "เลขโต๊ะต้องไม่เกิน 10 ตัวอักษร" });
}
```

### แก้ไข #3: ตัวจัดการข้อผิดพลาดกลาง (`src/app.js`)

**โค้ดก่อนแก้:** ไม่มี ระบบใช้ตัวเริ่มต้นที่ตอบเป็นหน้าเว็บพร้อมข้อความภายใน

**โค้ดหลังแก้:**

```js
app.use((err, req, res, next) => {
  if (err.type === "entity.parse.failed") {
    return res.status(400).json({ error: "รูปแบบข้อมูลที่ส่งมาไม่ถูกต้อง (JSON)" });
  }
  console.error(err);                                          // บันทึกไว้ดูเองในเซิร์ฟเวอร์
  res.status(500).json({ error: "เกิดข้อผิดพลาดภายในระบบ" });  // ผู้ใช้เห็นแค่ข้อความสั้น ๆ
});
```

**ผลทดสอบ #2 และ #3 ก่อน/หลังแก้:**

| คำขอ | ก่อนแก้ | หลังแก้ |
|---|---|---|
| ทานที่ร้าน ไม่ใส่เลขโต๊ะ | รับออเดอร์ (201) | **ปฏิเสธ (400)** "กรุณาระบุเลขโต๊ะ" |
| เลขโต๊ะยาว 30 ตัวอักษร | ระบบพัง (500) | **ปฏิเสธ (400)** |
| เงินที่รับเป็นข้อความ `"abc"` | ระบบพัง (500) | **ปฏิเสธ (400)** |
| เงินที่รับเป็นข้อความ `"500"` | รับไว้ (201) | **ปฏิเสธ (400)** |
| ข้อมูล JSON เสีย | หน้าเว็บมีข้อความภายในระบบ | **ตอบข้อความสั้น ๆ (400)** |
| สั่งปกติ (กลับบ้าน / ทานที่ร้านมีเลขโต๊ะ) | สำเร็จ (201) | สำเร็จ (201) |

|---|---|---|
| US-01 รับออเดอร์ | ไม่มีรายการ / ราคา ≤ 0 / จำนวน ≤ 0 ต้องถูกปฏิเสธและไม่บันทึก, ยอดรวมถูกต้อง | ผ่าน |
| US-02 ประเภทการทาน | ทานที่ร้านไม่ใส่โต๊ะต้องแจ้ง "กรุณาระบุเลขโต๊ะ", กลับบ้านไม่ต้องใส่โต๊ะ | ผ่าน |

| US-05 ตรวจวัตถุดิบ | ของพอต้องยืนยันและหักสต็อกได้, ของไม่พอต้องแจ้ง "วัตถุดิบไม่เพียงพอ" และไม่มีออเดอร์ค้าง | ผ่าน |
| US-06 บันทึกออเดอร์ | สถานะชำระแล้ว, ส่งให้บาริสต้า (รอทำ), มีเลขที่ใบเสร็จ | ผ่าน |
| อื่น ๆ | ยกเลิกออเดอร์แล้วคืนสต็อกได้, ออเดอร์ที่ใช้วัตถุดิบหลายตัวยังหักสต็อกได้ครบ | ผ่าน |

และรันชุดทดสอบ IDOR / SQL Injection / Error Handling ซ้ำ **ผ่านครบ 20 จาก 20 ข้อ**

## 4. แผนการแก้ไขที่เหลือ

| ความเสี่ยง # | ระดับความรุนแรง | เหตุผลที่ยังไม่แก้ | แนวทางที่ควรทำต่อ |
|---|---|---|---|
| #4 ไม่ตรวจขนาดของข้อมูล (ระบบตอบ 500 แทน 400) | Low | ไม่ทำให้ข้อมูลเสียหายหรือรั่ว และต้องแก้หลาย endpoint | จำกัดความยาวและค่าสูงสุด, ตรวจวันที่จริง, ตอบ 400 พร้อมข้อความที่ชัดเจน |
