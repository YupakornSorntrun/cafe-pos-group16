## 2. หน้าจอที่ทำ (Frontend ในโฟลเดอร์ `public/`)
ใช้ HTML + CSS + JavaScript ล้วน (ไม่ใช้ framework) ออกแบบตามเทมเพลต POS ที่เลือก คือแถบเมนูไอคอนด้านซ้าย การ์ดสินค้ามีรูป และแผงรายการสั่งซื้อด้านขวา ทุกหน้ามีตัวเลือกสาขา

| หน้า | ไฟล์ | ผู้ใช้ | ทำอะไรได้ |
| :--- | :--- | :--- | :--- |
| เข้าสู่ระบบ | `login.html` | ทุกคน | ล็อกอินแล้วเข้าหน้าของบทบาทตัวเอง |
| POS รับออเดอร์ | `index.html` | แคชเชียร์ | เลือกเมนู, ทานที่ร้าน/กลับบ้าน, เลขโต๊ะ, ส่วนลด, ชำระเงิน, เงินทอน, ใบเสร็จ, ดูและยกเลิกออเดอร์วันนี้ |
| จัดการเมนู | `menu.html` | เจ้าของ | เพิ่ม/แก้ไข/ลบเมนู, อัปโหลดรูป, กำหนดสูตรวัตถุดิบ |
| สต็อกวัตถุดิบ | `stock.html` | เจ้าของ | เพิ่ม/แก้ไข/ลบวัตถุดิบ, เติมสต็อก, ดูรายการใกล้หมด |

- เวลาในใบเสร็จและรายงานแสดงเป็นเวลาไทย

## 3. ระบบล็อกอินและสิทธิ์ (JWT)
- ล็อกอินด้วยชื่อผู้ใช้/รหัสผ่าน ได้ JWT มาเก็บไว้ในเบราว์เซอร์ แล้วแนบไปกับทุกคำขอ (`Authorization: Bearer ...`)
- รหัสผ่านเก็บแบบ hash (scrypt) ไม่เก็บรหัสจริง และล็อกอินผิดเกิน 5 ครั้งจะถูกล็อกชั่วคราว
- แยกสิทธิ์ที่ **ฝั่ง server** (ไม่ใช่แค่ซ่อนปุ่ม): แคชเชียร์รับออเดอร์ได้อย่างเดียว ผูกกับสาขาตัวเอง ส่วนเจ้าของจัดการเมนู สต็อก และดูแดชบอร์ดทุกสาขา
- แคชเชียร์ส่ง `branchId` / `employeeId` มาเองไม่ได้ ระบบใช้ค่าจาก token แทน (กันการสวมสาขา/พนักงานอื่น)

## 4. การปรับปรุง API (Backend)
- **เมนู**: เพิ่มรูปสินค้า (`image_url`) และสูตรวัตถุดิบ บันทึกพร้อมเมนูใน transaction เดียว; ลบเมนูที่เคยถูกขายแล้วไม่ได้ (แจ้งเหตุผล)
- **อัปโหลดรูป** `POST /api/uploads/menu-image`: รับ JPG/PNG/WEBP ไม่เกิน 2 MB เฉพาะเจ้าของ
- **วัตถุดิบ** `/api/ingredients`: เพิ่ม/แก้ไข/ลบ/เติมสต็อก (บันทึกประวัติใน `stock_movements`)
- **ออเดอร์**: `GET /api/orders/:id` ส่งรายการสินค้า+ใบเสร็จ+สาขา สำหรับพิมพ์ใบเสร็จ, `GET /api/orders` กรองตามสาขา/วันที่ได้
- **ยกเลิกออเดอร์** (`DELETE /api/orders/:id`): แคชเชียร์ยกเลิกได้เฉพาะออเดอร์ที่บาริสต้ายังไม่เริ่มทำ และคืนสต็อก ส่วนเจ้าของยกเลิกได้ทุกออเดอร์ แต่ถ้าเริ่มทำไปแล้วจะไม่คืนสต็อก (วัตถุดิบถูกใช้จริง) ตรวจสถานะซ้ำภายใน transaction เพื่อกัน race
- **เลขคิวรายวัน** (A001, A002, …): เริ่มใหม่ทุกวันแยกตามสาขา ออกเลขด้วยตารางตัวนับใน transaction เดียวกับการสร้างออเดอร์ ทดสอบยิง 12 ออเดอร์พร้อมกันได้เลขไม่ซ้ำ
- **เวลาไทย**: ตั้ง connection ของ MySQL เป็น +07:00 ทำให้ `NOW()` และข้อมูลที่เก็บเป็นเวลาไทย

## 5. การปรับปรุงฐานข้อมูล (Schema & Seed)
- `menu_items.image_url` (รูปสินค้า)
- `employees.username`, `employees.password_hash` และ role ใหม่ `owner`
- `orders.queue_date`, `orders.queue_no` (unique ต่อสาขา/วัน) และตารางใหม่ `branch_daily_counters` → ตอนนี้มี **11 ตาราง**
- `seed.sql`: ปรับเป็นร้าน **Baristech Cafe** 6 สาขา (บางแสน, ชลบุรี, ระยอง, ตราด, นนทบุรี, อยุธยา), เมนู 6 รายการต่อสาขา, วัตถุดิบ 11 ตัว, สูตรวัตถุดิบของทุกเมนู, บัญชีทดลองเจ้าของ 1 บัญชีและแคชเชียร์ 6 บัญชี (สาขาละ 1) และชื่อไฟล์รูปเริ่มต้นของเมนู (วางไฟล์ใน `public/images/menu/`)

## 6. การทดสอบ (Testing)
- ทดสอบ API ด้วย curl บนฐานข้อมูล MySQL ชั่วคราว: ล็อกอิน, สิทธิ์ของแต่ละบทบาท (แคชเชียร์ลบเมนู/ดูออเดอร์ทั้งหมดไม่ได้), สร้างเมนูพร้อมสูตร แล้วขายและตรวจว่าสต็อกลดถูกต้อง, ยกเลิกออเดอร์ทั้งกรณีคืน/ไม่คืนสต็อก, ยกเลิกซ้ำ, เลขคิวที่ยิงพร้อมกัน
- ทดสอบหน้าเว็บในเบราว์เซอร์: ล็อกอินเป็นเจ้าของและแคชเชียร์, เพิ่มสินค้าลงตะกร้า, ชำระเงินสด, ใบเสร็จ, เพิ่มเมนูพร้อมรูปและสูตร, ยกเลิกออเดอร์ในหน้าออเดอร์วันนี้, หน้าสต็อกและหน้ารายงาน
- **ยังไม่ได้ทดสอบ**: เลขคิวข้ามวัน (รีเซ็ตเป็น 001), หน้าจอบนมือถือ/จอเล็ก, การพิมพ์ใบเสร็จจริง, กรณีวัตถุดิบไม่พอผ่านหน้า UI

## 7. ข้อจำกัดที่ทราบและแนวทางต่อไป
- **วัตถุดิบใช้ร่วมกันทุกสาขา** (สต็อกก้อนเดียว) ตาม schema สัปดาห์ที่ 7 ควรแยกสต็อกรายสาขาด้วยตาราง `branch_ingredient_stock`
- ยังไม่มีหน้าจอบาริสต้า (FR-03) สถานะ "กำลังทำ" ต้องแก้ในฐานข้อมูลเอง
- JWT เก็บใน localStorage ตามที่เรียน ระบบจริงควรใช้ cookie แบบ `httpOnly`
- รายงานสรุปที่ฝั่ง client จาก `GET /api/orders` ส่วน `GET /api/reports/sales` ไว้ทำสัปดาห์ที่ 13
- ต้องปรับ ER Diagram สัปดาห์ที่ 7 ให้เป็น 11 ตาราง
- ไม่ได้ทำการแบ่งหมวดหมู่วัตถุดิบตามที่เจ้าของร้านต้องการ (FR-05) เพราะ schema ยังไม่มีหมวดของวัตถุดิบ

4. เปิด `http://localhost:3000/login.html` — เจ้าของ: `owner` / `owner123`, แคชเชียร์: `cashier1`–`cashier6` / `cashier123`
